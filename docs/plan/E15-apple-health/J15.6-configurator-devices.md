# J15.6 Configurator device and origin integration

Epic: [E15 Apple Health Bridge (required, v0.2.0)](README.md) · Status: done (2026-10-04) · Depends on: J15.2, J11.4, J11.5
Read: [apple-health#origins-and-relays](../../architecture/apple-health.md#origins-and-relays), [frontend#navigation](../../architecture/frontend.md#navigation)

**Objective:** Manage devices and origins from the web UI.

## Outputs
- Settings › Devices (pairing QR, list, requested types, last sync, possibly-denied flags, anchor reset, revoke)
- Origin classification feeding `known_relay_origins`; origin filter in coverage; origin/device chips in the rule builder

## Notes
- Classification is stored on the origin (`PATCH /origins/{id}` sets `data_origins.relayed_provider_id`); `known_relay_origins` stays the global seed for new origins, so one owner's edit does not change another's defaults.
- "Possibly denied" is per connection (paired devices share one): a requested type with no raw payload for 7 days, on a device paired and seen within that time.
- E2E: `web/e2e-stack/devices.spec.ts` (real server, seeded by `scripts/e2e-stack.sh`) and `web/e2e/devices.spec.ts`, `rule-chips.spec.ts` (stubbed API).

## Done when
- E2E with synthetic data: pair a fake device, classify an origin as a relay, build "Apple Watch HR first, exclude relayed".
