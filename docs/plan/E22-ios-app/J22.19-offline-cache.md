# J22.19 Offline read cache

Epic: [E22 Vitamux iOS app](README.md) · Status: done · Depends on: J22.4
Read: [ios-app#offline-cache-widgets-and-notifications](../../architecture/ios-app.md#offline-cache-widgets-and-notifications)

**Objective:** The app opens and shows the last data it saw without a network, clearly marked, and never keeps more than it should.

## Outputs
- A small file cache in VitamuxKit's `Core/` (one type, no database): GET responses for an allow-list of endpoints (dashboard layout and summary, inventory, metric ranges, specialised views, lab results, connections), keyed per server, user and request, in the app group container with file protection `completeUntilFirstUserAuthentication`.
- Stale-while-revalidate in the client: cached first, then fresh; screens show "as of <time>" and an offline banner. Mutations need the network and say so.
- A fixed 100 MB cap; the oldest files go first. It never caches PDFs, secrets, API-key or recovery-code responses, or exports.
- Cleared on sign-out, server change, `401` and from preferences; excluded from iCloud backup.

## Done when
- Tests: offline launch to a cached dashboard; eviction at the cap; nothing cached outside the allow-list; sign-out empties it.

## Notes
- One type, `ResponseCache` in `VitamuxKit/Core`: a `ClientMiddleware` inside `SessionMiddleware` that is also the file store. Keys are a SHA-256 of server, bearer token and path with query, so a new session never reads an old one's answers. The allow-list is by operation ID; Watch waveforms and routes stay out, as do documents, exports, auth, settings and keys.
- Stale-while-revalidate is network first with the stored answer as the fallback (no network, a transport error or a 5xx), so a request still gets one answer and screens need no cache code. Without a network a request fails at once, so an offline launch shows the cache immediately. A pull to refresh (`ResponseCache.refreshing`, on Dashboard and Explore) never falls back.
- The marker: an answer from the cache carries `Vitamux-Cached-At`, and `ResponseCache.status` drives the shell's "Offline, showing data from <time>" banner, which also says changes need the network. Mutations fail with "Can't reach the server".
- Cleared by `logout` and any `401` in the middleware (so a widget's client does the same), by every sign-in (covers a server change) and from Settings › This app, which shows its size. Least recently used goes first (file modification time, touched on read); one answer may use at most a quarter of the cap.
- UI tests switch the fake server's failure mode (`FakeServer.isOffline`) with `vitamux://uitest/offline` and `…/online`.
