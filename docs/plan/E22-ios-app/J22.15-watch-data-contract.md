# J22.15 Apple Watch data contract (ADR-0024)

Epic: [E22 Vitamux iOS app](README.md) · Status: todo · Depends on: None
Read: [ios-app#apple-watch](../../architecture/ios-app.md#apple-watch), [ADR-0014](../../adr/0014-healthkit-contract.md), [apple-health#payload](../../architecture/apple-health.md#payload), [metric-catalog](../../architecture/metric-catalog.md)

**Objective:** Agree on how every Apple Watch data type travels and where it is stored, before the kit and the normalizer are built in parallel, as [J15.1](../E15-apple-health/J15.1-platform-contract.md) did for v1.

## Outputs
- **Platform check** against Apple's HealthKit docs and the current SDK headers: every type Apple Watch writes, whether a third-party app may read it, its iOS version, its read API (anchored query, `HKElectrocardiogramQuery`, `HKHeartbeatSeriesQuery`, `HKWorkoutRouteQuery`, `HKActivitySummaryQuery`, `HKStateOfMind`), and how deletions show up. Unknowns go to the [device checklist](../../apple-health-device-checklist.md).
- **ADR-0024**, recording:
  - type registry v2 and the phone's groups, with sensitive groups off by default;
  - the optional payload fields (`ecg`, `beats`, `route`, `workout.events`, `workout.activities`, `state_of_mind`) and page sizes;
  - activity summaries: a 7-day re-read keyed by a UUIDv5 of the day;
  - storage with no new tables: `measurements`, `health_events` (plus `file_blob_sha256`), `workouts` and `workout_segments`, blobs for waveforms and routes;
  - read endpoints for waveforms and routes;
  - what stays out and why (clinical records, anything that needs another entitlement).
- `schemas/healthkit-samples.v1.json` extended with optional fields only, plus synthetic examples in `fixtures/`.
- [metric-catalog](../../architecture/metric-catalog.md) rows marked for E22; [apple-health](../../architecture/apple-health.md) payload and mapping updated.

## Done when
- The owner accepts ADR-0024.
- The extended schema validates both the v1 fixtures and the new ones, so the v1 contract still holds.
