# J22.3 Backend: native connection auth, pairing and version checks

Epic: [E22 Vitamux iOS app](README.md) · Status: done · Depends on: J22.1, J22.2
Read: [connectors#oauth-connection-flow](../../architecture/connectors.md#oauth-connection-flow), [ios-app#connecting-sources-from-the-phone](../../architecture/ios-app.md#connecting-sources-from-the-phone), [apple-health#pairing-and-security](../../architecture/apple-health.md#pairing-and-security)

**Objective:** The few server changes a native client needs beyond sessions: OAuth that returns to the app, pairing without a QR, and a version handshake.

## Outputs
- **OAuth for apps:** `POST /providers/{provider}/auth/begin` and `/connections/{id}/auth/begin` accept `{"return": "app"}` (app sessions only). The `oauth_states` row records it. The answer's `redirect_url` points to `GET /oauth/{provider}/start?ticket=…` (public, single use, short TTL), which sets the `vitamux_oauth` binding cookie in the auth browser and redirects to the provider.
- **Callback:** for an app-originated state it redirects to `vitamux://connections?connected=<provider>` or `?auth_error=<code>`; the browser path is unchanged. The scheme is a constant.
- **Prompt steps:** a test proves `auth/continue` works with a bearer session and the binding cookie from a cookie jar.
- **Pairing:** `POST /devices/pairing-codes` from an app session works without `VITAMUX_PUBLIC_URL` and then omits `qr_payload`.
- **Version handshake:** `GET /api/v1/system/version` adds `api_version` (an integer raised on breaking changes for clients) and `min_app_version` the server expects; the app refuses or warns on a mismatch.

## Done when
- Integration test: an app-originated Withings flow against `testutil/fakeprovider` ends at the `vitamux://` URL with the connection active; a replayed ticket or state fails.
- The browser OAuth e2e still passes unchanged.
- The authz matrix covers the new route.
